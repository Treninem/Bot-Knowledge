## Принципиальные границы
1. **Все приложения могут понимать общие языковые принципы**, включая распознавание риска и правила. Но только боты с полномочиями `chat_moderators` получают модерационный пакет и могут передать **подтверждённое** решение своему модерационному движку. Универсальная программа не становится модератором от скачивания файла.
2. В примерах отметка `candidate_violation` означает **кандидата на проверку**, а не наказание. Даже однозначная фраза требует версии локального правила, контекста, доказательств, полномочий и настроенного режима.
3. **Обучение** = сбор сигналов с согласованием и локальной изоляцией, сводка в абстрактные правила, удаление личного контекста, отдельный защищённый PR. GitHub публичен, а история Git сохраняет удалённые строки. Сырые переписки в репозиторий запрещены.
4. Новые JSON являются **обучающими примерами**, а не моделью понимания языка. Разработчик должен подтвердить поведение живой модели на разных текстах, включая неизвестные, а не только на примерах из пакета.
5. **Отчёт только по доказательствам**: файлы/числа, ссылка на коммит или PR, завершённый exact-head CI, main и отдельный post-main CI, отдельно статус подключения к потребителям.

## Проверка корректности и производительности
- Детерминированные тесты: уникальность идентификаторов и фраз, структура 63/44/33, 21 категория модерации с равными классами, корректный SHA, аудитории, 10 разных локальных поисковых проверок.
- Метрики модели для каждого consumer: количество ошибочных банов (цель **нулевое** на валидационном наборе), доля ложных предупреждений, пропущенные нарушения, английская речь, уместность юмора и реакции на траур. Не выдумывать проценты без измерения.
- Производительность: учитывать время загрузки + hot lookup отдельно. Не путать локальный тест GitHub runner с нагрузкой на BotHost или слабое устройство.
- При ошибке индекса или хэша: не использовать новый пакет, перейти на последнюю валидную локальную версию.
