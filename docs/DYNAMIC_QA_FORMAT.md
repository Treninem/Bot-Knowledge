# Самоописываемые справочные разделы: qa.v1

`qa.v1` — общий формат коротких проверенных вопросов и ответов. Потребитель,
который уже реализует этот контракт, может получить следующую тему обычным
обновлением манифеста и пакета. В клиенте не нужен список имён каждой новой
темы. Новый **способ обработки** данных, например иной `adapter`, требует
отдельной поддержки и проверки; одно описание раздела её не создаёт.

Формат предназначен для переносимой справки и языковых объяснений. Он не
заменяет узкую специализацию Bot-Knowledge, не превращает репозиторий в архив
переписок и не даёт ботам прав записи, модерации или исполнения действий.
Правила [POLICY.md](../POLICY.md) и
[проверенной публикации](LEARNING_PUBLICATION_PIPELINE.md) сохраняются.

## Файлы и первый пример

- [schema/qa.v1.schema.json](../schema/qa.v1.schema.json) описывает структуру.
- [templates/qa_v1.json](../templates/qa_v1.json) — валидный синтетический шаблон
  вне манифеста. Его копируют в новый пакет и заменяют собственным материалом.
- [packs/ru/knowledge_format.json](../packs/ru/knowledge_format.json) — настоящий
  общий раздел о формате: 10 разных вопросов и 10 дополнительных одобренных
  формулировок ответов. В нём нет данных отдельных пользователей или сообществ.
- `scripts/validate_qa_v1.py` проверяет ограничения, которые зависят от нескольких
  полей: уникальные ID, область применения, сопоставление полей, URL и лимиты.
  Он подключён к существующему `scripts/validate_pack.py`.

Минимальная запись и описание раздела:

```json
{
  "schema_version": 1,
  "language": "ru",
  "pack_version": "2026.11.02.8",
  "catalog": {
    "schema_version": 1,
    "id": "example_general_reference",
    "title": "Общий справочный раздел",
    "description": "Проверенные переносимые объяснения одной темы.",
    "purpose": "reference",
    "language": "ru",
    "adapter": "qa.v1",
    "records": "records",
    "audiences": ["all_ai_bots"],
    "contexts": ["direct", "private", "group_addressed"],
    "constraints": {
      "read_only": true,
      "requires_direct_address": true,
      "no_personal_data": true
    }
  },
  "records": [{
    "id": "example_record",
    "question": "Для чего нужен учебный пример пакета?",
    "aliases": ["Зачем нужен пример qa.v1?"],
    "answer": "Учебный пример показывает структуру проверяемого пакета вопросов и ответов.",
    "variants": ["По учебному примеру можно проверить структуру своего пакета вопросов и ответов."]
  }]
}
```

Значения версии в примере иллюстративны. Для публикации выбирают следующую
версию относительно актуального `main`, а хэши вычисляют по окончательным
байтам файлов.

## Описание раздела

| Поле `catalog` | Значение и предел |
| --- | --- |
| `schema_version` | Целое число `1` |
| `id` | Уникальный во всём снимке ASCII ID, шаблон `[A-Za-z0-9][A-Za-z0-9_-]{0,95}` |
| `title`, `description`, `purpose` | Непустые строки до 120, 700 и 80 символов; обычное назначение — `reference` |
| `language` | `ru`, `en` или `multilingual` |
| `adapter` | Для этого формата строго `qa.v1` |
| `tags` | Необязательный список: до 16 строк по 64 символа |
| `records` | Имя массива верхнего уровня; по умолчанию `records` |
| `audiences` | Непустой список до 12 строк по 64 символа; по умолчанию `all_ai_bots` |
| `contexts` | Непустое подмножество `direct`, `private`, `group_addressed`; по умолчанию только `direct` |
| `constraints` | Ровно три флага из примера, каждый строго `true` |
| `fields` | Необязательное безопасное сопоставление названий полей, описанное ниже |

`private` означает режим **выдачи общей справки** в личном диалоге. Оно не
разрешает помещать личные сведения в публичный пакет. `group_addressed` требует
явного обращения и разрешённого локального контекста. Потребитель проверяет
свои реальные права самостоятельно; данные не могут установить эти факты.

Метаданные рекомендуется хранить внутри пакета: тогда они покрыты его SHA-256.
Совместимый потребитель также может читать `catalog` из записи манифеста.
Если описание есть в обоих местах, его JSON-значения должны совпадать целиком;
конфликт отвергается. JSON Schema пакета описывает рекомендуемую встроенную
форму; manifest-only форму дополнительно проверяет реестр валидаторов.

## Записи вопросов и ответов

| Поле | Значение и предел |
| --- | --- |
| `id` | Обязательный уникальный внутри раздела ID того же формата, что `catalog.id` |
| `question` | Обязательный непустой вопрос до 500 символов |
| `aliases` | До 16 одобренных равнозначных вопросов по 500 символов |
| `answer` | Обязательный непустой ответ до 1600 символов |
| `variants` | До 8 дополнительных одобренных ответов по 1600 символов |
| `source` | Необязательная публичная HTTPS-ссылка до 500 символов |
| `audiences`, `contexts` | Необязательное сужение соответствующих областей раздела |
| `language` | Необязательное уточнение языка; иной язык разрешён только внутри `multilingual` |
| `constraints` | Необязательное повторение тех же трёх строгих ограничений |

В одной публикации — 1–1000 записей в пакете; в индексе общего `qa.v1` — не
более 4096 записей. Предельный размер пакета совместимого потребителя —
1 МиБ; всего снимка — 4 МиБ и 64 пути. Не расширяйте пределы публикацией
переименованного дубликата. Варианты одного ответа обязаны сохранять факты,
числа, отрицания и оговорки; их редакторская проверка не заменяется схемой.

Ответ отдаётся как экранированный текст. После HTML-экранирования каждый
вариант должен укладываться в 2000 символов. Чтобы последующая обработка
клиента не обрезала существенные оговорки, рекомендуется писать короче
1500 символов. HTML, команды и фигурные скобки не создают инструкций или
подстановок. Источник не загружается автоматически. Для публикации используется
общедоступный URL без учётных данных, параметров запроса и фрагментов с
идентификаторами; валидатор требует URL без query/fragment вообще.

Сопоставление вопроса ограничено регистром, пробелами, `ё/е`, завершающими
знаками и поддерживаемыми вводными вроде «что такое». Это не нечёткий поиск
произвольных фактов. Разные числа и отрицания не удаляются. Если одинаковый
ключ ведёт к разным ответам, совместимый потребитель отказывается выбирать
произвольно и может попросить явный раздел.

## Существующие названия полей

Для уже подготовленного плоского набора разрешена декларативная запись:

```json
{
  "records": "entries",
  "fields": {"id": "key", "question": "prompt", "answer": "response"}
}
```

Это фрагмент `catalog`, а не отдельный пакет. Допустимы только имена
`id`, `question`, `aliases`, `answer`, `variants`, `source`, `audiences`,
`contexts`, `constraints`, `language`, сопоставленные уникальным одиночным
полям вида `[A-Za-z][A-Za-z0-9_]{0,63}`. Несопоставленные поля сохраняют свои
обычные названия. Путь к вложенному объекту, выражение, функция, регулярное
выражение или шаблонизатор не допускаются. Для переименованной коллекции и
полей обязательна семантическая проверка `validate_qa_v1.py` наряду со схемой.

Существующий `reply_catalog.json` остаётся в своём действующем формате с
`question/section/when/avoid/audiences`. Его нельзя объявлять плоским `qa.v1`:
потеряются условия уместности. Совместимый consumer обязан читать эти уже
существующие поля как данные, не выполнять их как команды и не требовать
перестройки каталога ради нового набора ответов.

## Границы доверия

На любой глубине запрещены поля исполняемых действий, полномочий и инструментов:
`action/actions`, `auto_apply`, `execute`, `permissions`, `command/commands`,
`code`, `template`, `template_eval`, `tool/tools`. Сохраняются запреты на
персональные идентификаторы, имена пользователей, секреты и исходные сообщения.
Есть пределы глубины 10, размера объекта 80 полей и списков 1000 элементов.
Автоматическая проверка подозрительных строк служит дополнительной защитой;
смысловую приватность, достоверность и отсутствие скрытых инструкций проверяет
редактор до PR. Боты не публикуют собственную память этим форматом.

Неизвестный `adapter` может оставаться видимым в каталоге как `unsupported`,
но его записи не становятся ответами. Неверный известный формат получает
статус `invalid` или отклоняет обновление по политике потребителя. Последний
исправный локальный снимок и встроенный fallback остаются необходимыми.

## Добавление следующего раздела

1. Взять свежий `main`, проверить назначение и отсутствие аналогичного раздела.
2. Скопировать шаблон в `packs/ru/<новая_тема>.json`, задать уникальные ID,
   редакторски проверенные вопросы, варианты, источники и ограничения.
3. Увеличить `pack_version` и `knowledge_version`. Добавить новый путь в
   `manifest.json`, сохранив остальные записи и их SHA; обновить `generated_at`.
4. Вычислить SHA-256 **окончательных байтов** нового или изменённого пакета.
   Пробелы, переводы строк и кодировка входят в хэш. Не пересериализовывать
   старые пакеты только ради форматирования.
5. Выполнить `python scripts/validate_pack.py`,
   `python scripts/test_dynamic_contracts.py` и
   `python -O scripts/test_dynamic_contracts.py`; затем существующие проверки
   затронутых читателей. Проверить алиасы, сужение областей, отрицательные
   инъекции и получение ответа реальным совместимым клиентом.
6. Пройти действующий PR / exact-head CI / утверждение / post-main процесс.
   Успех локальной проверки и наличие файла в `main` отдельно от доставки
   обновления работающему боту.

Этот контракт описывает совместимость данных. Он не является заявлением,
что все действующие боты уже получили новый потребитель или снимок.
