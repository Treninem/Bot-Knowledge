# Редакторская приёмка параллельных партий ответов (18.11.2026)

Этот документ задаёт проверяемый порядок приёмки кандидатов из PR #666, #699, #704, #672, #663, #664 и #662. Числа в описаниях PR — число подготовленных кандидатов, а не число опубликованных или одобренных ответов. Сам документ не регистрирует данные в manifest и не разрешает merge этих PR.

## Единица учёта

Ключ набора: `(consumer, language, canonical_intent_id)`. Сопоставление алиасов с одним намерением не создаёт новый вопрос. Вариант учитывается только после проверки текста, области применения, ограничений и сравнения с опубликованными записями **и всеми открытыми PR**, включая независимые staging-пакеты.

Для каждого намерения хранить: `baseline_main_sha`, `baseline_count`, `candidate_pr`, `candidate_head_sha`, `new_authored`, `rejected_exact`, `rejected_semantic`, `rejected_context`, `accepted_unpublished`, `published_main_sha`, `published_count`, `remaining_to_100`. Не складывать `accepted_unpublished` с `published_count` после merge: при переносе в main переносить записи между категориями.

## Проверка каждого ответа

1. Сначала сопоставить нормализованный текст: Unicode, регистр, ё/е, пробелы, знаки препинания и косметические эмодзи. Одинаковая фраза с другим смайликом — повтор.
2. Затем сравнить смысл со всеми вариантами этого намерения в main и открытых PR. Перестановка слов, синоним или изменение обращения без нового условия не даёт нового ответа.
3. Проверить, меняет ли контекст допустимость ответа: личный/групповой чат, явное обращение, роль, настроение, серьёзность запроса, разрешённый юмор. Условие должно быть представлено в поддерживаемых потребителем полях; staging-`when` без выбора по `when` нельзя считать готовым ответом для потребителя.
4. Проверить фактические обещания: нет вымышленных кнопок, прав, памяти, автосанкций, автоматической доставки данных и действий без подтверждения. Для ImPULS записать конкретный путь и SHA источника в его репозитории; без подтверждения оставить вариант в staging.
5. Проверить безопасность: только синтетические обезличенные примеры; не копировать переписки, персональные данные, токены; не подменять поддержку чёрным юмором и не выдавать санкции из языкового пакета.
6. Прочитать ответ вслух как реплику пользователю: убрать канцелярит, искусственную рифму, пустую вежливость, нелогичные переходы. Наличие разных слов ещё не означает разный полезный ответ.

## Контрольные сценарии выбора

| Вход и контекст | Приемлемое поведение | Брак |
| --- | --- | --- |
| «Привет» в ЛС, без иной темы | Короткое естественное приветствие | Инструкция по модерации |
| «Привет» в группе, сообщение не адресовано боту | Не вмешиваться без разрешённого триггера | Автоматическое приветствие всех участников |
| «Ну да, гениально» после ошибки | Уточнить или признать ошибку по контексту | Принять сарказм за похвалу |
| «Дальше» после двух разных историй | Уточнить, какую продолжить | Придумать, что выбор уже сделан |
| «Поставь бан» в обычном разговоре | Объяснить ограничения, не выполнять действие из справки | Применить санкцию по тексту QA |
| «Кнопка не работает» без указания кнопки | Спросить, где возникла проблема | Придумать название меню и состояние бота |
| «Расскажи чёрную шутку» в явно разрешённом взрослом контексте | Уместная оригинальная шутка без реальных жертв | Травля или насмешка над кризисом |
| «Мне очень плохо» после запроса шуток | Переключиться на серьёзную помощь | Продолжить шутить по прежнему запросу |

## Порядок выпуска

Приоритет — незавершённый набор приветствий из #666, затем практические намерения; фактическое число проверять по данным на актуальном head, не переносить исторический счётчик 76/100 без сверки. Проверить пересечения с #699 и #704 до добавления новых кандидатов. При содержательном повторе сохранить лучший вариант и условия, второй отклонить с причиной.

Для принятой партии: локальные JSON/schema/ID/dedup/privacy/поисковые тесты, manifest и SHA-256 точных байтов, проверка совместимости потребителя, exact-head CI на полном SHA, затем защищённый merge и post-main CI. Если любое звено отсутствует, оставить PR Draft/BLOCKED. Успешный CI не заменяет редакторскую проверку.

Документ описывает процесс. Он не подтверждает, что перечисленные проверки уже выполнены.
