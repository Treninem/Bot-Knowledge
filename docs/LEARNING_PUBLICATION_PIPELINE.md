# Безопасное обучение и публикация новых знаний в GitHub

**Цель владельца:** все ИИ-потребители способны обнаруживать переносимые полезные навыки; общая библиотека получает их без потери приватности. **Текущий статус**: правила, offline-CLI кандидата, проверка и изолированный trusted publisher для reviewed `qa.v1`. Живой бот по-прежнему не получает write-токен и не пишет в GitHub напрямую.

## Двухконтурная схема
```text
Чат → приватный контекст конкретного продукта (без GitHub-токенов)
     → локальные агрегаты/повторяющиеся исправления (TTL, согласие)
     → обобщение в короткое правило без исходных цитат
     → независимая проверка приватности/качества + synthetic tests
     → `scripts/prepare_knowledge_candidate.py` (локальная проверка)
     → доверенный публикатор отдельной учётной записи
     → новая ветка/PR → exact-head CI → ручное утверждение → main CI
     → HTTPS-манифест, SHA-256, локальный cache/rollback у каждого бота
```

## Ограничения
- **Не** делиться секретами, именами, реальными сообщениями, ID, локальными правилами, обвинениями и действиями против конкретных участников.
- Отдельный бот **не имеет** прав записи `main`. Его формулировка — только кандидат. Защищённый публикатор `scripts/trusted_publish_qa.py` может создать ветку и **draft PR** после подтверждённого обзора. Он запускается только в изолированном maintainer-окружении с `BK_TRUSTED_PUBLISHER=1`; рядом с bot token запуск запрещён. Старый `--merge-if-green` теперь **явно отклоняется до создания PR**, так как немедленная проверка асинхронного CI небезопасна. После редакторской проверки используется отдельный `scripts/complete_trusted_qa_pr.py`: ожидает успешный exact-head CI, проверяет исходный head/base, содержимое двух файлов, SHA-256, безопасно завершает PR только по явному поручению доверенного maintainer и проверяет post-main CI. См. [TRUSTED_QA_PUBLISH_COMPLETION.md](TRUSTED_QA_PUBLISH_COMPLETION.md).
- Исходные кейсы должны быть синтетическими и разнообразными, избегать дублей и пустых перефразирований.
- Классификация тонов, сарказма, мата и обходов **не** является санкцией.
- Скрипт фильтра — дополнительная защита, **не гарантия анонимности**: каждый кандидат требует человеческого редакторского обзора.

## Формат кандидата
```json
{
  "candidate_id": "shared_rule_example",
  "statement": "Не считать короткую цитату оскорблением без контекста и локального правила.",
  "when": ["сообщение содержит цитату другого участника"],
  "avoid": ["цитата является частью прямой атаки на адресата"],
  "audiences": ["chat_moderators"],
  "origin": "synthetic",
  "reviewed": true
}
```
Запуск только **в доверенном изолированном окружении**, не над сырым логом:
```sh
python scripts/prepare_knowledge_candidate.py --input /tmp/candidate.json --output /tmp/approved_candidate.json
```
Результат находится **вне публичного репозитория**. Далее доверенный maintainer сверяет содержание и подбирает существующий `qa.v1` раздел. Для уже reviewed записи `scripts/trusted_publish_qa.py` проверяет структуру, публичный HTTPS-source, признаки персональных данных, дубли и возможные противоречия; затем обновляет действующий пакет, SHA и manifest и создаёт draft PR. Токен передаётся только этому отдельному процессу через окружение и не устанавливается в ImPULS/BotHost. При спорном совпадении публикация останавливается кандидатом.

Локальный `scripts/build_skill_draft.py` собирает только проверяемый черновик пакета и манифеста из уже рассмотренного кандидата и точного reviewed skill. Вывод создаётся вне базового репозитория; перед выдачей проходит существующий preflight. Скрипт не отправляет PR, не имеет токена записи и не заменяет редакторское решение. Живой publisher по-прежнему не реализован.

## Единый формат каждого отчёта
`дата | head SHA | уже в main? | файлы | новые уникальные записи | удалённое/изменённое | точный CI (тесты запущены?) | post-main CI | доставлено в какие боты | блокеры/следующий безопасный шаг`.
Отдельно считать только **новые** материалы, не перефразированные копии. При отказе Actions запуск без шагов — `BLOCKED`, а не `PASS`.


## Обязательные regression gates для reviewed-skill tooling — 02.11.2026

Существующие офлайн-инструменты `preflight_skill_manifest.py` и
`build_skill_draft.py` имеют собственные синтетические тесты. Эти тесты теперь
входят в основной quality workflow, чтобы зелёный main действительно проверял
их после любого изменения репозитория. Отдельный read-only workflow
`reviewed-skill-tools.yml` проверяет их непосредственно на SHA head PR и
сверяет фактический checkout.

Изменение не добавляет новые знания, не меняет manifest или cache и не даёт
потребителям токены записи. Текущая авторизация владельца разрешает доверенному
maintainer-процессу самостоятельно сливать проверенные PR Bot-Knowledge, но
живые боты по-прежнему не получают write-доступ и не публикуют сырые чаты.
